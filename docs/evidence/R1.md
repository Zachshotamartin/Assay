## Semantic review and contract reconciliations

Golden semantic review: canonical evidence now records complete run and task
identity binding, task policies and effective seeds, and the corrected
unsafe-host lifecycle without synthetic sandbox events.

The regenerated golden was reviewed rather than accepted as hash churn. Its
run record binds the project-relative suite path and suite content hash; every
task id, task hash, repetition count, seed strategy, root seed, and derived
seed; the full declared variant identity; config hash; simulated adapter id,
version, contract version, and tier; provider-reported model identity;
invocation root seed; harness and pricing-catalog versions; status; and the
`unsafe_host` isolation label. Task-run records bind repetition, retry attempt,
and effective seed. The SQLite uniqueness key correspondingly includes run,
task, repetition, and attempt.

The frozen `RunRecord` sketch in `BUILD_PLAN.md` section 3.4 retained older,
incomplete aliases such as a scalar variant and seed. Product requirement
FR-RUN-007 requires the complete comparability identity, and the more specific
Build Plan section 6.3 prose, Methodology section 13, and Architecture sections
3.5 and 7.1 agree. The implementation therefore removed the incomplete aliases
and records the complete binding; this is a precedence reconciliation, not a
silent weakening of evidence.

`TASK_FORMAT.md` formerly said suite results ordered only by id, while the
higher-precedence `BUILD_PLAN.md` sections 6.4 and 6.6 fix ordering by source
path then id. The task-format document and implementation now use the Build
Plan contract.

The hostile-config pre-schema item ceiling changed from 10,000 to 1,000. A
valid v1 config has only 17 leaves, so the lower bound preserves all valid
inputs while making hostile-input rejection deterministic under full-suite CPU
contention. The rejection test remains enabled and strict.

No test was weakened, skipped, deleted, or marked flaky to obtain these
results. Remediation changed implementations, expanded corpora and property
coverage, or reconciled contracts according to the normative precedence rules.

## Exit-code ownership boundary

FR-RUN-010 defines all seven product exit categories: 0 success, 1 task
failure, 2 budget breach, 3 comparison regression, 4 invalid input or
configuration, 5 infrastructure error, and 6 cancellation. The detailed R1
evidence matrix in `BUILD_PLAN.md` section 6.6 explicitly requires subprocess
coverage for 0, 1, 4, 5, and 6. Exit 2 depends on the R5 budget evaluator and
exit 3 on the R6 comparison engine; neither later-gate subsystem exists in R1.
The broader R1.13 and section 6.9 wording says every documented exit code, so
R1 does not claim that criterion complete and does not invent placeholder
budget or comparison behavior to make 2 or 3 reachable early.
